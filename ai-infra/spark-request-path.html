Spark Request Path

Two ways in, one place where the key is checked, and one hop that runs on a clock.

Reading it in one pass

The connector on the OrangePi dials out to Cloudflare and keeps four QUIC connections open. A request from anywhere lands on the edge and is pushed back down one of those, so no port is opened at home and no firewall rule exists. The OrangePi then makes an ordinary LAN call to the head node — it hosts nothing itself, and LiteLLM sees every remote caller as 192.168.7.100.

A request from the house skips the top two boxes and goes straight to spark-db71.local:4000 by name. Same destination, same key required, no external dependency. Only the connector needs the literal IP, because cloudflared cannot resolve mDNS. fleet_llm_base picks between the two automatically by probing the LAN with a one-second timeout.

The one that bites

vLLM on :8000 has no auth at all. LiteLLM is the entire security boundary — anything that exposes :8000 beyond the LAN exposes the cluster with no key.

Kill switch

Power off the OrangePi and the public endpoint disappears. LAN serving keeps running untouched, and nothing on the Spark nodes had to change to expose them in the first place.

Why an IP, not a name

The connector's origin is 192.168.7.103 because cloudflared uses Go's resolver and cannot resolve mDNS .local names. It is a DHCP lease, so a reservation is still owed.
